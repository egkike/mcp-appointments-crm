# Feature: Owner-in-chat (B12) — owner persona skill v1.1 + gateway per-sender enablement + operator steps

**Type**: package (skill template feature + docs contract + operator steps) — owner-approved 2026-10-19
**Branch**: TBD (skill/docs → docs or code lane per routing; TUI operator steps are owner hands)
**Status**: doc-first phase (delegated)
**Origin**: backlog **B12** (`odd/tasks/backlog.md`) — product gap discovered during the B2 bonus: the Telegram owner channel (feature 1.21) has owner-only plumbing but the skill v1.0 (1.22) never implemented the owner persona; every owner chat behaves as a client-service conversation.

## Specs

- **S1 (owner persona in skill v1.1)**: owner said verbatim: "no tiene sentido que me trate como un cliente normal en el canal del bot de telegram si soy yo el owner el único que se puede conectar por telegram... habíamos habilitado el telegram justamente para que solo el owner pueda pedir todo desde ahí... además de poder hacerlo también desde Whatsapp." The skill template `setup/templates/recepcionista-negocio/SKILL.md` must gain a TWO-persona procedure: client persona (current v1.0, unchanged) and OWNER persona selected when the conversation arrives on the owner-private Telegram bot channel (and, once the gateway per-sender exists, when the WhatsApp sender resolves to `accounts` owner). Owner persona permits operating the business via the existing owner-only MCP tools (update_business_profile, create/update/delete_service, create/update_professional, upsert/delete_schedule, hours-exception create/delete/list).
- **S2 (deletes double-gate, owner decision)**: deletes via chat (`delete_service`, `delete_schedule`, `delete_hours_exception`) are allowed for the owner persona ONLY behind an explicit double confirmation gate in-chat (confirm action + confirm permanence — the pürg pattern). Owner decision verbatim (paraphrase of the selected option): "owner puede borrar servicios/schedules/horas-exceptions via chat con doble confirmación explícita".
- **S3 (TUI-only hard scope)**: the owner persona MUST NOT operate via chat: `purge-inactive` (accounts purge), account deactivation, Transfer Ownership, audit log listing. These stay admin-TUI-only by design (singletons/destructive/permanent; the audit trail keeps recording, but never renders in chat). The skill v1.1 must say so explicitly ("por estos pedidos te derivo a la consola de administración").
- **S4 (gateway per-sender — Hermes-side boundary)**: implement the `docs/gateway-contract.md` protocol with per-sender `X-Caller-Id` injection and the 401→register_client→retry loop (owner phone in `accounts` resolves owner role; any other phone resolves client via `clients.id == phone`; unknown → registration loop). **This repo has NO gateway implementation surface** (verified 2026-10-19: scripts/ holds install.sh + tests only; the gateway is Hermes-platform code). In THIS repo the deliverable is: the gateway-contract doc updated with the owner-persona interaction rules + the acceptance checklist the Hermes build must satisfy; the gateway build itself runs in the Hermes codebase (separate repo, owner-owned).
- **S5 (operator steps)**: Transfer Ownership of the demo owner (`+5491100000000`) to the owner's real phone (`+5492617132740`) via the admin TUI (supported today), then `messenger_platform` → `whatsapp` in the business profile (via owner tools/TUI). Both owner hands; the change documents the exact TUI sequence + post-conditions.
- **S6 (cascade re-apply)**: skill v1.1 ships inside the repo template (source of truth); re-running option 7 on installed hosts detects the template差 (SkillStateModified) and offers the replacement with the B9 attribution warning — already verified live during the B2 smoke; no new code needed, document the operator step.

## Constraints & fences

- **Versioning**: the skill frontmatter version bumps to 1.1.0 with the persona rules; `render`-safe charset rules (entity `BusinessNameHasUnsafeChars`) continue to apply to the business name placeholder; `{business_name}` stays the only templated variable.
- **Identity boundary (unchanged)**: the server never learns a sender from Telegram (anonymous user id only) — the owner persona on Telegram keys on CHANNEL (the owner-private bot), never on a phone the bot can see; on WhatsApp it keys on the per-sender resolved role later.
- **RBAC double enforcement unchanged**: the composition-root tool map + in-usecase `auth.RequireRole` stay the backstop; the skill persona is behavioral guidance, never a security layer.
- **The client persona contract stays untouched** (B2-verified behaviors: saludo sin tool, registro loop, privacidad).
- All artifacts keep the repo's layering contract (ADR-0013): no server code changes expected in this feature; if the doc-first discovers a code need (e.g., a server-side gate for owner-persona ops), it must surface as an explicit S with evidence before implementation.
